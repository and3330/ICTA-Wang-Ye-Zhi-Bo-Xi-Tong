# 場次手動補發上線通知

## 使用方式

直播間 → 排程 → 場次管理 → 該場次的「補發上線通知」。

每次可選「該場次全部報名者」或「該場次尚未出席者」，確認收件人數後送出。
信件標題為「【要上線囉】直播間標題」，附上收件人自己的觀看連結。

- 同一場次同一 Email 合併寄一封，使用該場次最新的有效報名。
- 封存報名仍有效；已刪除的報名不寄。
- 尚未出席模式會排除同 Email 同場次已有任何有效出席紀錄的人，並在寄送前重查。
- 未發佈、已取消、已結束的場次不能建立補發；場次或報名失效後也不再寄送。
- 每個場次至少間隔 60 秒才能建立另一批通知。
- 手動補發不改動自動提醒開關或排程。
- 成功回應表示已加入背景寄送排程，不代表信已送達或已讀。

## 管理端 API

這些是現有登入 session 保護的管理端端點，只有直播間主辦者或有效超級管理員可操作。
不是外部唯讀 MCP 的工具，也不接受外部整合密鑰作為授權。

### 預覽人數

`GET /api/webinars/{webinarId}/sessions/{sessionId}/notifications/preview?audience=all`

`audience` 必填：`all`（全部）或 `absent`（尚未出席）。
回應不含收件人的個資或觀看憑證，並設定 `Cache-Control: no-store`。

```json
{
  "recipientCount": 2,
  "audience": "all",
  "scheduledStart": "2030-01-01T11:30:00.000Z",
  "timezone": "Asia/Taipei"
}
```

### 確認補發

`POST /api/webinars/{webinarId}/sessions/{sessionId}/notifications`

```json
{
  "audience": "all",
  "requestId": "11111111-1111-4111-8111-111111111111",
  "expectedCount": 2
}
```

```json
{
  "batchId": "11111111-1111-4111-8111-111111111111",
  "queuedCount": 2,
  "replayed": false
}
```

`requestId` 是每次確認操作的新 UUID，不是登入憑證。批次與全部收件工作以同一交易建立。
同一操作者、直播間、場次、對象重試相同 `requestId`，會取得原批次及 `replayed: true`，不重複建立工作。
斷線或伺服器錯誤時，留在原視窗重試；不要以新 UUID 自動重送。

錯誤一律為 `{"message":"說明"}`：

- `400`：參數錯誤。
- `401/403`：未登入、帳號不可用或無操作權限。
- `404`：場次不屬於指定直播間或不存在。
- `409`：無收件人、人數已變動、場次不可補發，或重試內容與原批次不符。人數變動時需重新確認再送。
- `429`：同場次補發間隔不足，附上 `Retry-After: 60`。
- `500`：處理失敗；沿用同次 `requestId` 重試。

## 測試與發佈

後端測試以伺服器端注入的遠期時鐘建立工作，避免真實開發寄信 worker 搶走測試工作。
瀏覽器測試使用真實人數預覽，但攔截確認寄送；實際 HTTP 入列、去重及寄前資格判斷由資料庫整合測試驗證。

發佈需套用新增通知批次資料表、寄信工作批次欄位及唯一索引；保留正式資料，不覆蓋開發資料。
